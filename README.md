# Second Brain Framework

> 多 Agent 协同 + 持久记忆 + 治理规则 + 本地主权 的个人知识管理体系

## 这是什么

一套为**长期、跨领域、强治理**项目设计的 AI Agent 协作框架。不是"AI 助手"，是"AI 团队"。

核心特征：
- **多 Agent 分工**：调研、执行、编码各有专职 Agent，不混岗
- **持久记忆**：跨会话不丢失工作上下文，Agent 不再"每次重启都失忆"
- **治理规则自动化**：权威源管控、阈值闸口、交接留痕、复盘反哺——不是写在文档里的纪律，是 Agent 执行时自动遵守的技能包
- **本地主权**：数据不出本机/NAS，完全自主可控

## 适用场景

| 适合 | 不适合 |
|---|---|
| 长期迭代项目（周/月级） | 一次性小任务 |
| 跨领域项目（调研+代码+数据） | 单一领域项目 |
| 需要强治理的项目 | 快速原型验证 |
| 多 Agent 协作场景 | 单 Agent 够用的小项目 |

## 架构概览

```
你（决策者）
├── 日常决策 Agent ← 拆方案、列清单、验收
├── 高级推理 Agent ← 硬骨头方案再审
── 统一调度入口 ← 路由任务、管理 MCP、维护会话
│   ├── 记忆后端 ← 跨会话持久记忆
│   ├── 书记 Agent ← 工作记忆 + 检索/归档
│   ├── 执行 Agent ← 工作流、批量任务
│   └── 编码 Agent ← 写代码、搭流程
└── 后方基础设施
    ├── 本地模型 ← 敏感数据、不联网任务
    ├── 对话界面 ← 可视化交互
    └── 记忆容器 ← 持久化存储
```

详见 [docs/architecture.md](docs/architecture.md)。

## 治理体系

| 技能包 | 管什么 |
|---|---|
| `authority-ledger` | 数据写哪、谁是准的 |
| `threshold-gate` | 什么时候才准改架构 |
| `project-init` | 新子项目怎么立项 |
| `handoff` | 换 Agent/换会话怎么交接 |
| `retro` | 做完怎么复盘、新信号怎么回写 |
| `security-policy` | Agent 权限边界 + 四干预点拦截（pre_tool_call/input/output/post_tool_call） |

详见 [docs/governance.md](docs/governance.md)。

## 快速开始

### 1. 部署记忆后端

```bash
# 在 NAS 或服务器上
bash deploy/deploy-agentmemory.sh
```

### 2. 配置统一调度入口

在调度入口的 MCP 配置中添加：

```json
{
  "mcpServers": {
    "agentmemory": {
      "command": "docker",
      "args": ["exec", "-i", "agentmemory", "npx", "-y", "@agentmemory/mcp"],
      "env": {
        "AGENTMEMORY_URL": "http://127.0.0.1:3111",
        "AGENTMEMORY_SECRET": "<YOUR_SECRET>"
      }
    }
  }
}
```

### 3. 安装治理技能包

将 `skills/` 目录复制到各 Agent 的技能目录中。

## 为什么不是单 Agent

单 Agent 的问题：
- **上下文会爆**：调研+代码+测试全塞一个窗口，注意力衰减
- **不够专**：一个模型不可能同时是顶级研究员+顶级程序员
- **不能并行**：调研和写代码只能串行
- **成本不优**：所有任务都用最强模型

多 Agent 的优势：
- **专业化**：各司其职
- **上下文分散**：每个 Agent 只装自己那部分
- **可并行**：调研和编码同时进行
- **成本优化**：调研用便宜模型，推理用强模型

详见 [docs/architecture.md](docs/architecture.md) §多 Agent vs 单 Agent。

## 完整示例：开发一个记账 APP

以下示例展示整个框架如何协作完成一个真实项目。所有数据均为虚构。

### 场景

决策者提出需求："我要做一个能上架 App Store 的记账 APP，目标用户是大学生，核心功能是 AA 制分摊和账单提醒。"

### 流程

#### 第 1 步：日常决策 Agent 拆方案

日常决策 Agent 收到需求后：
1. 查询记忆后端："决策者以前做过 APP 吗？有没有技术栈偏好？"
   - → 召回：2 个月前做过一个 Web 应用，用的 React + Vite
2. 拆方案：
   - 技术选型：SwiftUI（原生）vs React Native（跨平台）
   - 上架流程：Apple Developer 账号 → TestFlight → App Store Review
   - 合规要求：隐私政策、数据收集披露、年龄分级
3. 输出方案清单，问决策者确认几个关键决策

#### 第 2 步：高级推理 Agent 再审（按需）

方案里有个硬骨头："AA 制分摊的算法设计，涉及多人实时结算，可能有循环债务问题。"

日常决策 Agent 把这个扔给高级推理 Agent："帮我想想这个结算算法怎么设计最合理。"

高级推理 Agent 返回：图论 + 最小化转账次数的算法方案。

#### 第 3 步：统一调度入口路由任务

统一调度入口接到任务后：
1. 查记忆后端："上次做 Web 应用时踩过什么坑？"
   - → 召回：CDN 加载超时、localStorage 缓存清理问题
2. 分配任务：
   - **书记 Agent**：负责调研 App Store 上架流程、整理合规清单
   - **执行 Agent**：负责跑批量任务（比如批量生成测试数据）
   - **编码 Agent**：负责写代码（SwiftUI 项目脚手架）

#### 第 4 步：治理技能包自动约束

书记 Agent 开始调研前，治理技能包自动触发：

| 技能包 | 触发场景 | 动作 |
|---|---|---|
| `authority-ledger` | 要写调研数据前 | 查台账：调研结果写哪？→ `子项目/记账 APP/调研/` |
| `project-init` | 新子项目立项 | 走七步：一句话定位、不做什么、权威源、阈值、环境、权衡、交接产出物 |
| `threshold-gate` | 想选技术方案前 | 查阈值：有没有"技术栈必须原生"的信号？→ 没有，可以选 React Native |

书记 Agent 输出：
- 立项文档：`子项目/记账 APP/立项文档.md`
- 调研结论：App Store 审核平均 24-48 小时，需要隐私政策 URL

#### 第 5 步：编码 Agent 写代码

编码 Agent 接到任务："搭建 SwiftUI 项目脚手架"

1. 查记忆后端："上次 React 项目用的什么目录结构？"
   - → 召回：`src/components/`、`src/hooks/`、`src/utils/`
2. 参考 `codebase-design` 技能：深模块设计
3. 输出：
   ```
   iOS-Ledger/
   ├── App/
   ├── Features/
   │   ├── SplitBill/
   │   └── Reminders/
   ├── Core/
   │   ├── Models/
   │   └── Services/
   └── Resources/
   ```

#### 第 6 步：执行 Agent 跑批量任务

执行 Agent 接到任务："生成 100 条测试账单数据"

1. 跑 Python 脚本：`python tools/generate_test_data.py --count 100`
2. 输出：`tests/fixtures/mock_bills.json`
3. 自动记录到记忆后端："生成了 100 条测试数据，用于单元测试"

#### 第 7 步：归档 + 记忆写入

任务完成后：

| 组件 | 动作 |
|---|---|
| **书记 Agent** | 把调研文档归档到 `子项目/记账 APP/调研/` |
| **记忆后端** | 自动记录："2026-10-07 立项记账 APP，技术选型 SwiftUI，上架流程已调研" |
| **阈值登记** | 更新：子项目数 +1，代码行数 +X |
| **权威源台账** | 新增：`iOS-Ledger/` 主拷贝在服务器 `/data/code/iOS-Ledger/` |

#### 第 8 步：下次会话的连续性

一周后决策者问："记账 APP 进展到哪了？"

书记 Agent 从记忆后端召回：
- "2026-10-07 立项，技术选型 SwiftUI"
- "App Store 审核需要隐私政策 URL"
- "编码 Agent 搭建了项目脚手架"
- "执行 Agent 生成了 100 条测试数据"

书记 Agent 回答："上周完成了立项和脚手架搭建，调研了上架流程。下一步是开发核心功能（AA 制分摊），需要 Apple Developer 账号（$99/年）。要继续推进吗？"

## 治理技能包触发示例

### 示例 1：权威源台账触发

**场景：** 编码 Agent 想把编译产物提交到 Git。

**触发 `authority-ledger`：**
1. 查台账：编译产物的主拷贝在哪？
2. 台账显示：编译产物是派生拷贝，主拷贝是源代码
3. 规则：派生拷贝不进 Git，只进 `.gitignore`
4. 动作：编码 Agent 自动把 `build/` 加入 `.gitignore`

**结果：** 避免了把 500MB 编译产物提交到 Git。

---

### 示例 2：阈值闸口触发

**场景：** 执行 Agent 发现项目文件超过 1000 个，想拆分子目录。

**触发 `threshold-gate`：**
1. 查阈值表：文件数阈值是 > 2000 才触发重构
2. 当前实测值：1000 个文件
3. 判定：未触发 → 按住不动
4. 输出："文件数 1000，阈值 2000，未触发。不建议拆分。"

**结果：** 避免了过早优化，保持项目结构简单。

---

### 示例 3：交接留痕触发

**场景：** 书记 Agent 要换班，由另一个 Agent 接手后续工作。

**触发 `handoff`：**
1. 生成交接文档，包含 7 节：
   - 现状：立项完成，脚手架搭好，调研完成
   - 冻结决策：技术选型 SwiftUI，不上 React Native
   - 未完成项：核心功能开发、TestFlight 测试、App Store 提交
   - 环境前提：需要 Xcode 15+、Apple Developer 账号
   - 阈值状态：文件数 1000/2000，未触发
   - 红线约束：编译产物不进 Git、隐私政策 URL 必须有效
   - 是否值得继续投入：是，决策者已批准
2. 接手 Agent 读取交接文档，无缝继续

**结果：** 接手 Agent 不需要重新调研，直接从"核心功能开发"开始。

---

### 示例 4：复盘反哺触发

**场景：** 记账 APP 项目完成第一阶段，进行复盘。

**触发 `retro`：**
1. 回顾：第一阶段完成了立项、脚手架、调研
2. 归因：调研耗时比预期长，因为 App Store 审核规则经常变
3. 新信号：发现"审核规则变更频率"是个新信号
4. 回写：在阈值登记新增信号 F1："App Store 审核规则变更 > 3 次/季度 → 建立规则追踪机制"
5. 改进措施：书记 Agent 每月检查一次 App Store 审核指南更新

**结果：** 复盘的发现变成了可执行的治理规则，下次项目自动受益。

## 防腐烂机制示例

### 问题：记忆只进不出， eventually 会膨胀

### 解决方案

| 机制 | 如何工作 | 示例 |
|---|---|---|
| **去重** | 300 秒内相同工具调用只记一次 | 编码 Agent 连续 3 次运行同一个测试，只记 1 次 |
| **观察压缩** | LLM 把每条观察压缩成摘要 | "运行测试 100 个，通过 98 个，失败 2 个" → "测试通过率 98%" |
| **会话压缩** | 会话结束自动合并为记忆 | 50 条观察 → 1 条记忆："完成脚手架搭建" |
| **捕获过滤** | 过滤敏感字段 | API Key、password 等字段自动过滤 |
| **阈值告警** | 条目数/磁盘占用超阈值时提醒 | 记忆条目 > 10,000 → 提醒评估归档策略 |

### 实际效果

| 时间 | 原始观察数 | 压缩后记忆数 | 压缩率 |
|---|---|---|---|
| 第 1 周 | 500 | 50 | 90% |
| 第 1 月 | 2,000 | 200 | 90% |
| 第 3 月 | 6,000 | 600 | 90% |

**没有压缩：** 6,000 条观察，检索慢，噪声多
**有压缩：** 600 条记忆，检索快，噪声少
