# 治理规则说明

## 为什么需要治理

多 Agent 协作的最大风险不是"做不好"，而是"做乱了"——数据乱放、架构乱改、交接无留痕、复盘无回写。治理规则把"纪律"从文档里的建议变成 Agent 执行时自动遵守的约束。

## 五大治理机制

### 1. 权威源台账（authority-ledger）

**管什么：** 每类数据的"唯一真相源"在哪。

**核心规则：**
- 写入只进主拷贝，不得直接写派生拷贝
- 派生拷贝单向对账，禁止反向修正主拷贝
- 四项必填字段缺一即阻塞：数据类、主拷贝位置、派生拷贝及方向、一致性级别

**触发场景：** 任何 Agent 要写入、修改、同步数据时。

### 2. 撑不住阈值闸口（threshold-gate）

**管什么：** 什么时候才允许改架构。

**核心规则：**
- 想改架构/拆文件/加索引/扩硬件 → 先查阈值表
- 信号未触发 → 按住不动，本表就是"为什么不改"的凭据
- 信号已触发 → 才允许进入重构
- 禁止登记"感觉该重构了"这类无信号改动冲动

**触发场景：** 任何 Agent 想改动架构、拆分文件、增加索引时。

### 3. 立项七步（project-init）

**管什么：** 新子项目怎么立项。

**七步流程：**
1. 一句话定位
2. 不做什么（明确边界）
3. 权威源（数据主拷贝在哪）
4. 阈值信号（什么信号触发重构）
5. 环境前提（依赖什么，如何验证）
6. 权衡表（关键决策的取舍理由）
7. 交接产出物（跨 Agent 必须产出什么文档）

**触发场景：** 启动新子项目、新工作线时。

### 4. 交接留痕（handoff）

**管什么：** 换 Agent/换会话时怎么交接。

**核心规则：**
- "我记得"不算留痕，必须产出交接文档
- 交接文档必须包含 7 节：现状、冻结决策、未完成项、环境前提、阈值状态、红线约束、是否值得继续投入
- 红线约束转达时原文照抄，不得改写

**触发场景：** 换 Agent、换会话、暂停工作线时。

### 5. 复盘反哺（retro）

**管什么：** 做完怎么复盘，新信号怎么回写。

**核心规则：**
- 新信号必须回写阈值表，不许只留在复盘文件里
- 改进措施必须可执行、可验证、有负责人、有复核日期
- 反哺优先：复盘产出的新信号，必须回写阈值表

**触发场景：** 会话结束、工作线完成、或用户要求复盘时。

### 6. 安全策略与干预点（security-policy）

**管什么：** Agent 的权限边界，以及在四个关键干预点拦截越权操作。

**四个干预点：**

| 干预点 | 触发时机 | 检查内容 |
|---|---|---|
| `pre_tool_call` | 工具调用前 | 工具名、参数是否越权 |
| `input` | 数据写入前 | 路径、内容类型是否合规 |
| `output` | 数据输出前 | 是否含凭据/PII |
| `post_tool_call` | 工具调用完成后 | 实际结果是否符合预期 |

**核心规则：**
- 先拦截，再执行。干预点未通过不得继续操作
- 越权请求必须记录审计日志（支持 Markdown 表格 + JSON Lines 双格式）
- 凭据对 Agent 不可见，由调度层在请求发出时注入

**触发场景：** Agent 要访问外部网络、读写敏感路径、使用凭据、或执行系统命令时。

## 治理 vs 灵活性

治理不是限制创造力，是防止"做乱了"。核心原则：

| 原则 | 说明 |
|---|---|
| **先查表，再动手** | 想改任何东西，先查对应的治理表 |
| **没有信号 = 不许改** | 找不到触发条件的改动冲动，一律按住 |
| **反哺优先** | 复盘的新发现必须回写治理表，不能只留在复盘文件里 |
| **实测值必须带日期** | 超过 30 天的实测值在使用前须重测 |

## 完整示例：权威源台账实战

### 场景

编码 Agent 想把博客平台的编译产物（`dist/` 目录）提交到 Git 仓库。

### 触发 `authority-ledger`

1. **查台账**：编译产物的主拷贝在哪？
2. **台账显示**：
   - 数据类：博客平台编译产物
   - 主拷贝位置：`/data/blog/dist/`（本地构建生成）
   - 派生拷贝及方向：`dist/` → CDN 部署（单向）
   - 一致性级别：最终一致（重跑 `npm run build` 即对齐）
3. **规则**：派生拷贝不进 Git，只进 `.gitignore`
4. **动作**：编码 Agent 自动把 `dist/` 加入 `.gitignore`

### 结果

避免了把 500MB 编译产物提交到 Git，保持仓库干净。

## 完整示例：阈值闸口实战

### 场景

执行 Agent 发现博客平台的项目文件超过 1000 个，想拆分子目录。

### 触发 `threshold-gate`

1. **查阈值表**：文件数阈值是 > 2000 才触发重构
2. **当前实测值**：1000 个文件（2026-10-07 实测）
3. **判定**：未触发 → 按住不动
4. **输出**："文件数 1000，阈值 2000，未触发。不建议拆分。"

### 结果

避免了过早优化，保持项目结构简单。

### 反例：如果阈值已触发

假设文件数达到 2500（超过阈值 2000）：

1. **判定**：已触发 → 允许进入重构
2. **动作**：执行 Agent 提出拆分方案，走立项七步
3. **输出**：`子项目/博客平台重构/立项文档.md`

## 完整示例：立项七步实战

### 场景

决策者提出："我想给博客平台加一个评论系统。"

### 执行七步

1. **一句话定位**：为博客平台添加评论功能，支持匿名评论和审核机制
2. **不做什么**：不做实时聊天、不做用户注册系统、不做社交分享
3. **权威源**：评论数据主拷贝在 `/data/blog/comments/`，派生到数据库（单向）
4. **阈值信号**：评论数 > 10,000 → 评估是否需要分页/缓存
5. **环境前提**：需要数据库支持（SQLite/PostgreSQL），必须实测连接
6. **权衡表**：
   | 决策 | 选了 | 没选 | 理由 |
   |---|---|---|---|
   | 存储方案 | SQLite | PostgreSQL | 博客流量小，SQLite 够用，部署简单 |
   | 审核机制 | 先审后发 | 先发后审 | 避免垃圾评论，博客规模小可承受审核延迟 |
7. **交接产出物**：评论系统 API 文档、数据库 schema、审核流程说明

### 产出物

- `子项目/博客评论系统/立项文档.md`
- 状态：草稿（待决策者批准）

## 完整示例：交接留痕实战

### 场景

书记 Agent 完成了博客平台调研，要换班由编码 Agent 接手开发。

### 触发 `handoff`

书记 Agent 生成交接文档：

```markdown
# 交接文档：博客平台开发

> 用途：本线明确会分阶段续做，按治理规则「跨 Agent/跨会话工作必须产出交接文档」建立本文件。
> 建立日期：2026-10-07
> 接手 Agent：编码 Agent

## 1. 一句话现状

调研完成，技术选型 Next.js + MDX，部署方案 Docker。待完成：脚手架搭建、核心功能开发。

## 2. 已冻结的决策（不得擅改）

| 决策 | 内容 | 依据 |
|---|---|---|
| 技术栈 | Next.js 14 + MDX | 决策者批准，SEO 友好 |
| 部署方案 | Docker 容器 | 决策者批准，便于迁移 |
| 数据库 | SQLite | 立项文档第 6 步权衡表 |

## 3. 未完成项（下次开工从这里接）

- 搭建 Next.js 项目脚手架
- 配置 MDX 支持
- 开发博客列表页、详情页
- 开发评论系统（见立项文档）
- Docker 部署配置

## 4. 环境前提警告

- 需要 Node.js 18+（必须实测，不得引用旧结论）
- 需要 Docker 环境（必须实测版本）
- 需要域名和 SSL 证书（决策者负责）

## 5. 阈值与"为什么不重构"

- 文件数：50/2000，未触发
- 依赖数：10/50，未触发

## 6. 红线约束（转达时原文照抄）

- 编译产物（`dist/`、`.next/`）不进 Git
- `.env` 文件不进 Git，只进 `.env.example`
- 数据库文件（`*.db`）不进 Git

## 7. 本线是否值得继续投入

是，决策者已批准立项。
```

### 结果

编码 Agent 读取交接文档，直接从"搭建 Next.js 项目脚手架"开始，无需重新调研。

## 完整示例：复盘反哺实战

### 场景

博客平台项目完成第一阶段，进行复盘。

### 触发 `retro`

1. **回顾**：第一阶段完成了调研、立项、脚手架搭建
2. **归因**：调研耗时比预期长，因为 Next.js 14 的 App Router 文档不清晰
3. **新信号**：发现"框架文档清晰度"影响调研效率
4. **回写**：在阈值登记新增信号：
   | # | 信号 | 阈值 | 实测值 | 判定 |
   |---|---|---|---|---|
   | G1 | 调研耗时超过预估 50% | > 50% → 建立文档质量评估机制 | 80%（实际 8 小时，预估 4.5 小时） | 已触发 → 建立文档质量评估 |
5. **改进措施**：书记 Agent 在调研前先评估框架文档质量，如果文档差则优先找社区教程

### 产出物

- `复盘/2026-10-07-博客平台第一阶段.md`
- 更新 `治理/阈值登记.md`（新增 G1 信号）

### 结果

复盘的发现变成了可执行的治理规则，下次项目自动受益。

## 防腐烂机制完整示例

### 问题：记忆只进不出， eventually 会膨胀

### 解决方案

| 机制 | 如何工作 | 示例 |
|---|---|---|
| **去重** | 300 秒内相同工具调用只记一次 | 编码 Agent 连续 3 次运行 `npm run build`，只记 1 次 |
| **观察压缩** | LLM 把每条观察压缩成摘要 | "运行测试 100 个，通过 98 个，失败 2 个" → "测试通过率 98%" |
| **会话压缩** | 会话结束自动合并为记忆 | 50 条观察 → 1 条记忆："完成脚手架搭建" |
| **捕获过滤** | 过滤敏感字段 | `.env` 里的 API Key 自动过滤，不写入记忆 |
| **阈值告警** | 条目数/磁盘占用超阈值时提醒 | 记忆条目 > 10,000 → 提醒评估归档策略 |

### 实际效果（虚构数据）

| 时间 | 原始观察数 | 压缩后记忆数 | 压缩率 |
|---|---|---|---|
| 第 1 周 | 500 | 50 | 90% |
| 第 1 月 | 2,000 | 200 | 90% |
| 第 3 月 | 6,000 | 600 | 90% |

**没有压缩：** 6,000 条观察，检索慢，噪声多
**有压缩：** 600 条记忆，检索快，噪声少

## 治理规则速查表

| 想做什么 | 先查什么 | 规则 |
|---|---|---|
| 写数据 | 权威源台账 | 写入只进主拷贝 |
| 改架构 | 阈值登记 | 信号未触发 → 按住不动 |
| 启动新项目 | 立项七步 | 必须走七步，产出立项文档 |
| 换 Agent/会话 | 交接留痕 | 必须产出交接文档，7 节缺一不可 |
| 项目结束/阶段完成 | 复盘反哺 | 新信号必须回写阈值表 |

## 常见问题

### Q: 治理规则会不会太严格，影响效率？

A: 治理规则只在关键节点触发（写数据、改架构、立项、交接、复盘），日常执行不受影响。而且规则是自动检查的，不需要人工盯。

### Q: 如果阈值设错了怎么办？

A: 阈值可以调整，但必须走立项七步，说明调整理由。防止随意改动。

### Q: 交接文档太长了，能不能简化？

A: 7 节是最低要求，每节可以写得很简短。关键是"冻结决策"和"红线约束"必须原文照抄，不能改写。

### Q: 复盘太耗时了，能不能不做？

A: 复盘可以简化，但"新信号回写阈值表"这一步不能省。否则治理体系会失去自我进化能力。
