# 架构说明

## 12 层指挥链

```
1.  你（决策者）          ← 最终决策、提出需求、裁决争议
2.  日常决策 Agent        ← 拆方案、列清单、验收产物（处理 80% 常规任务）
3.  高级推理 Agent        ← 硬骨头方案再审（按需调用，成本较高）
4.  统一调度入口          ← 路由任务、管理 MCP 连接、维护会话状态
5.  记忆协议层            ← 跨会话持久记忆总线（MCP 协议）
6.  书记 Agent            ← 工作记忆 + 检索/归档
7.  执行 Agent            ← 工作流、批量任务、脚本执行
8.  编码 Agent            ← 写代码、搭流程、架构设计
9.  后方基础设施          ← 物理边界（NAS / 本地服务器）
10. 本地模型              ← 敏感数据处理、不联网任务
11. 对话界面              ← 可视化交互入口
12. 记忆容器              ← 持久化存储后端（Docker 容器）
```

## 数据流示例

以"开发记账 APP"为例：

```
你 → 日常决策 Agent 拆方案
       ↓
       高级推理 Agent 审计算法设计
       ↓
统一调度入口 路由任务
  ├→ 书记 Agent：调研上架流程 → 归档到知识库
  ├→ 编码 Agent：搭建项目脚手架
  └→ 执行 Agent：生成测试数据
       ↓
记忆协议层 → 记忆容器：记录本次工作上下文
       ↓
下次会话 → 书记 Agent 从记忆容器召回历史 → 无缝继续
```

## 多 Agent vs 单 Agent

### 单 Agent 的问题

| 问题 | 说明 |
|---|---|
| 上下文衰减 | 即使 1M 上下文，中间部分的信息利用率也显著低于首尾 |
| 不够专 | 一个模型不可能同时是顶级研究员 + 顶级程序员 |
| 不能并行 | 调研和写代码只能串行 |
| 成本不优 | 所有任务都用最强模型，费用高 |
| 错误隔离差 | 一个环节出错，整个上下文可能被污染 |

### 多 Agent 的优势

| 优势 | 说明 |
|---|---|
| 专业化 | 各司其职，每个 Agent 优化特定能力 |
| 上下文分散 | 每个 Agent 只装自己那部分，不会爆窗 |
| 可并行 | 调研和编码同时进行 |
| 成本优化 | 调研用便宜模型，推理用强模型 |
| 错误隔离 | 一个环节出错不影响其他 |

### 什么时候用单 Agent

- 小型项目（< 3 天工作量）
- 单一领域项目（纯写代码、纯调研）
- 快速原型验证

### 什么时候用多 Agent

- 大型项目（> 1 周工作量）
- 跨领域项目（调研 + 代码 + 数据）
- 长期迭代项目（需要跨会话连续性）
- 强治理需求项目（不能乱改架构）

## 防腐烂机制

| 层 | 机制 | 作用 |
|---|---|---|
| 记忆容器 | 去重 | 300 秒内相同工具调用只记一次 |
| 记忆容器 | 观察压缩 | LLM 把每条观察压缩成摘要 |
| 记忆容器 | 会话压缩 | 会话结束自动合并为记忆 |
| 记忆容器 | 捕获过滤 | 过滤敏感字段（password/token 等） |
| 记忆容器 | 阈值告警 | 条目数/磁盘占用超阈值时提醒 |
| 调度入口 | 上下文压缩 | 上下文窗口快满时自动压缩早期对话 |

## 本地主权原则

- 敏感数据走本地模型处理，不经过云端
- 所有 Agent 通过统一调度入口管理，不各自为战
- 数据主拷贝位置明确，派生方向单向
- 认证密钥不写入配置文件或文档

## 真实场景演练：搭建一个博客平台

以下用一个虚构的"个人博客平台"项目，展示架构中每一层如何实际运作。

### 阶段一：立项（第 1-4 层）

**决策者**："我想搭一个支持 Markdown 的博客平台，能部署在自己的服务器上。"

**日常决策 Agent** 接活：
1. 查记忆 → "3 个月前做过一个静态站点生成器，用的 Hugo"
2. 拆方案 → 技术选型（Hugo vs Next.js vs Astro）、部署方案（Docker vs 裸机）、域名/SSL
3. 输出 3 个方案对比表，问决策者选哪个

**高级推理 Agent** 被调用（按需）：
- 决策者选了 Next.js，但 SEO 方案拿不准
- 高级推理 Agent 对比 SSR/SSG/ISR 三种渲染策略的 SEO 表现，给出推荐

### 阶段二：分工执行（第 5-8 层）

**统一调度入口** 路由任务：

| Agent | 任务 | 上下文窗口只装什么 |
|---|---|---|
| 书记 Agent | 调研 Next.js 博客最佳实践、SEO 方案、部署文档 | 只装调研相关上下文 |
| 编码 Agent | 搭建 Next.js 项目脚手架、配置 MDX、写博客组件 | 只装代码相关上下文 |
| 执行 Agent | 批量生成 50 篇测试文章、跑 Lighthouse 性能测试 | 只装脚本相关上下文 |

三个 Agent **并行工作**，互不阻塞。

### 阶段三：防腐烂（第 9-12 层）

**记忆容器** 全程记录：
- 去重：编码 Agent 跑了 10 次 `npm run build`，只记 1 次
- 压缩：50 条观察 → 5 条记忆（"完成脚手架"、"MDX 配置通过"、"Lighthouse 评分 95"…）
- 过滤：`.env` 里的 API Key 自动过滤，不写入记忆

**3 个月后**，决策者问："博客平台现在什么状态？"

书记 Agent 从记忆容器召回 → "Next.js 脚手架已搭好，MDX 配置通过，Lighthouse 评分 95，待完成评论系统和 RSS 订阅。"

无缝继续，不用重新交代。

## 上下文衰减实测

以下数据来自公开 benchmark（LongMemEval-S，500 问）：

| 召回模式 | R@5 | R@10 | NDCG@10 |
|---|---|---|---|
| BM25 + 向量混合 | 95.2% | 98.6% | 87.9% |
| 纯 BM25 | 86.2% | 94.6% | 73.0% |

**关键发现：** 即使有 1M 上下文，模型对中间部分信息的利用率也显著低于首尾（Lost in the Middle 效应）。多 Agent 分散上下文 = 每个 Agent 的上下文更短 = 注意力更集中。

## 成本对比：单 Agent vs 多 Agent

以"博客平台"项目为例（1 周工作量）：

### 单 Agent 方案

| 阶段 | 模型 | 上下文 | 估算成本 |
|---|---|---|---|
| 调研 | 最强模型 | 50K tokens | $0.50 |
| 算法设计 | 最强模型 | 80K tokens | $0.80 |
| 写代码 | 最强模型 | 200K tokens | $2.00 |
| 测试 | 最强模型 | 100K tokens | $1.00 |
| **合计** | | **430K tokens** | **$4.30** |

### 多 Agent 方案

| 阶段 | 模型 | 上下文 | 估算成本 |
|---|---|---|---|
| 调研 | 便宜模型 | 30K tokens | $0.03 |
| 算法设计 | 最强模型 | 20K tokens | $0.20 |
| 写代码 | 中等模型 | 150K tokens | $0.75 |
| 测试 | 便宜模型 | 50K tokens | $0.05 |
| **合计** | | **250K tokens** | **$1.03** |

**多 Agent 方案成本降低 76%**，同时调研质量更高（书记 Agent 专注调研）、代码质量更高（编码 Agent 专注代码）。

## 故障隔离示例

**场景：** 编码 Agent 在写博客组件时引入了一个 bug，导致构建失败。

### 单 Agent 方案
- 整个上下文被污染：调研结论、算法设计、测试数据都在同一个窗口里
- 修复 bug 时需要重新加载所有上下文
- 可能误改调研结论或测试数据

### 多 Agent 方案
- 只有编码 Agent 的上下文受影响
- 书记 Agent 的调研结论不受影响
- 执行 Agent 的测试数据不受影响
- 修复后只需重新调度编码 Agent，其他 Agent 无需重做

```

│                                                  │
│  ┌─────────────┐    ┌──────────────────────┐     │
│  │  统一调度入口  │───→│  记忆容器 (Docker)     │     │
│  │  (OpenClaw)  │    │  :3111 REST API       │     │
│  │  :29896      │    │  :3113 Viewer         │     │
│  └──────┬──────┘    └──────────────────────     │
│         │                                         │
│    ┌────┴────┬──────────┬──────────┐             │
│    │         │          │          │             │
│  书记      执行       编码      日常决策          │
│  Agent    Agent     Agent     Agent             │
│                                                  │
│  ┌─────────────┐    ┌──────────────────────┐     │
│  │  本地模型     │    │  对话界面             │     │
│  │  (Ollama)   │    │  (Open WebUI)         │     │

│  └─────────────┘    └──────────────────────┘     │
└──────────────────────────────────────────────────┘
```

所有数据流都在本地闭环，不经过任何外部服务（除非你主动配置 LLM Key 用于记忆压缩）。
